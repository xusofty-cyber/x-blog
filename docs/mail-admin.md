# 后台邮箱管理（v1 + v2 分组列表）

## v5：全部新邮件（统一视图，2026-11-09，提交 ec609e3，已部署）

- 入口：后台左侧“邮箱管理”最上方新增“全部新邮件”一行，点它进入统一视图；点下方任一邮箱则回到单个邮箱视图。统一视图里也有“返回单个邮箱”。
- 做法：后端新增 `GET /api/mail/recent?since=ISO&limitPerMailbox=20&maxTotal=100`（JwtAuthGuard，与其他邮箱接口一样只给管理员），一次拉全部邮箱在 `since` 之后收到的邮件，按时间倒序合并返回，最多 100 封、每邮箱最多 20 封；`since` 最多回溯 30 天，缺省为最近 24 小时。前端时间范围可选：自上次查看以来 / 最近 24 小时 / 最近 3 天 / 最近 7 天。
- “上次查看时间”存在浏览器本地（localStorage `xblog_unified_last_check`），不是服务器时间：第一次没有记录时默认按最近 24 小时。关键细节——**拉取本身不自动改这个时间**，否则一刷新列表就丢了；看完后点“已看完，更新上次查看时间”，下次“自上次查看以来”才从那时开始算。想找回漏看的，换“最近 7 天”即可。
- 性能与容错：每个邮箱用户名不同、必须单独登一次 IMAP，后端 4 路并发拉取（11 个分组、29 个邮箱约十几秒），单个邮箱失败（最常见是授权码过期）只进返回里的 `failed` 列表在页面上提示，不让整个聚合失败；已读/未读以各邮箱自己的 `\Seen` 状态为准。
- 统一视图里点开一封邮件、删除、下载附件都复用单个邮箱的接口（按该封所属邮箱的 id 走），点开即标记已读；每封下面都标了分组名与收件邮箱。原有单个邮箱的列表、搜索、分页、正文、删除、添加/更新分组一律未动。
- 部署核对（2026-11-09）：备份 `/home/ubuntu/xblog-backup-20261109-mail-recent.sql`（600）；部署前后一致：11 个分组、29 个邮箱、分组授权码总长度 726；健康 `{"status":"ok"}`，`/api/mail/recent` 未登录返回 401（路由已注册、鉴权在起作用），`/admin/mail` 200，部署日志 “Deployment completed successfully”。本次无数据库迁移。
- 待云中君在浏览器里实测：首次点“全部新邮件”才是第一次真正跨 29 个邮箱拉取（部署时只能验到路由与鉴权，拿不到管理员登录态去拉真实邮件），若某个邮箱拉取失败，页面会直接列出它是哪个邮箱、什么原因。

## v4：163 邮箱支持（无数据库迁移）

- 新增邮箱类型 `163`：163 邮箱走 `imap.163.com:993` SSL，用 163 网页邮箱里生成的客户端授权密码（非 163 登录密码），添加前需先在 163 设置里开启 IMAP 并生成该密码。
- 服务商由邮箱域名推断，不新增数据库列、不改现有 QQ 数据：`@163.com` -> `imap.163.com`，QQ 系（`@qq.com`、`@foxmail.com`）仍走 `imap.qq.com`，邮箱上存的 `imapHost` 即按此推断写入。
- 分组隔离：163 分组只能有 1 个邮箱，不能与 QQ 邮箱混在一个分组里，也不能把 QQ 邮箱加进 163 分组、或把 163 邮箱加进 QQ 分组；改邮箱、改类型时若跨服务商（QQ <-> 163）会直接拒绝，需删除后按新服务商重新添加。QQ 分组仍是最多 3 个、每类型一个、共用一个总授权码。
- 前端：新增分组表单里有“163 邮箱”选项，163 分组在左侧只显示分组标题一行（点标题即查看它唯一的邮箱，不再下方重复列一行），163 分组的更新面板里不再出现“再加一个邮箱”（已达 1 个上限）。
- 部署安全与之前一致：本次改动无 Prisma 迁移，部署前仍做数据库备份，部署后核对分组数、邮箱数与分组授权码总长度与部署前一致，密钥不换。

在 `/admin/mail` 切换多个 QQ 邮箱查看邮件。第一版只读加标记已读，不发件、不删除、不移动邮件，不在博客库里存邮件正文与附件，打开时按需经 IMAP 拉取。

## v3：分组总授权码 + 邮件删除 + 侧边栏不留白

- 一个 QQ 只有一个总授权码，数字、字母、Foxmail 三个邮箱共用：添加 QQ 时填一次总授权码，给该 QQ 加邮箱时不再填授权码，换码时在更新面板里填一次新总授权码，后端会用组下所有邮箱各测一次登录，任何一个失败都不保存。
- 邮件删除：列表每封邮件旁和正文顶部都有“删除”按钮，点后二次确认，后端经 IMAP 给邮件打 \Deleted 再按 UID 清除；删除后它将从收件箱消失，QQ 邮箱里一般可在已删除里找回，具体以 QQ 邮箱为准。
- 侧边栏留白修复：后台侧边栏改为固定视口高度（sticky top-0 h-screen），随页面滚动时仍停在左侧，不再随主内容拉长；邮箱列表不再设 45vh 上限，改为随侧边栏整体滚动，底部操作区始终在视口底部。
- 迁移 `20261102213000_group_authcode`：分组上加加密授权码列，把每组最早一个邮箱的加密授权码原样抄到分组上、收紧非空后，才删掉邮箱上的旧列；任何一步失败迁移整体回滚，不会先删后抄。部署前仍需备份，部署后核对分组数、邮箱数与分组授权码总长度与部署前一致。

## v2：侧边栏分组列表

- 切换不再用下拉框：后台左侧“邮箱管理”导航项下方就是按 QQ 分组的邮箱列表，点“邮箱管理”可以把列表收起来或展开。

## 后端

- NestJS 模块：`apps/api/src/mail/`，路由前缀 `/api/mail`，全部接口用现有 `JwtAuthGuard`，只给后台管理员。
- 账号模型：`MailAccount`（Prisma 迁移 `20261102195000_add_mail_account`），只存备注名、邮箱、IMAP 主机/端口与加密后的授权码。
- 加密：AES-256-GCM，密钥只来自服务器 `.env` 的 `MAIL_ENCRYPTION_KEY`（32 字节 base64 或 hex），不进仓库、不进日志、不进聊天。添加与换授权码时先测 IMAP 登录，通了才保存。
- IMAP：QQ 系 `imap.qq.com:993` SSL，163 系 `imap.163.com:993` SSL，每次请求新建连接、用完即断开；列表按页拉取信封，详情再解析全文与附件；附件超过 30MB 时后端拒绝，提示去邮箱下载。

## 前端

- 后台导航加“邮箱管理”，页面 `apps/web/app/admin/mail/page.tsx`：顶部下拉切换账号，左侧列表加搜索与分页，右侧正文用 `sandbox=""` 的 iframe 渲染 HTML（脚本被沙箱拦截），附件经带 Bearer 的 fetch 下载。

## 数据迁移安全（v2 必须遵守）

- 迁移 `20261102211000_add_qq_group` 是纯加法：新建 QqGroup 表、每个已有邮箱账号原地变成一个分组（分组 id 复用账号 id）、给 MailAccount 加分组与类型两列，**不删任何 MailAccount 行、不改 encryptedAuthCode**。
- 部署前不要重新生成 `MAIL_ENCRYPTION_KEY`：已有授权码是用服务器 .env 里那把密钥加密的，换了密钥就解不出来，等于全部授权码丢失。
- 部署前先给数据库做一次备份（例如 pg_dump 到服务器项目外或别处），迁移后再核对分组数与邮箱数与部署前一致。

## 服务器部署前置

部署前先确认服务器项目根 `.env` 里有 `MAIL_ENCRYPTION_KEY`，没有时在服务器上用 python3 生成并追加（不要把值发到聊天里，也不要写进仓库）：

```bash
python3 -c "import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())"
# 把输出追加为 MAIL_ENCRYPTION_KEY=... 到 .env（权限保持 600）
```

其余部署流程与手册一致：推 main、服务器跑 `deploy/deploy.sh`、健康检查。本次改动单独做，不捆种子文章与凭证有效期那批未部署改动。

## 站长使用步骤

1. 每个 QQ 号先在 QQ 邮箱设置里开启 IMAP 服务并生成授权码（不是 QQ 密码）。
2. 登录博客后台 `/admin/mail`，填备注名、QQ 邮箱与授权码，添加并测试通过后即可切换查看。
3. 换 QQ 密码后授权码会失效，在同一页更新授权码即可。
